# Jantra Security Notes

- Gemini keys are stored through Electron `safeStorage` and are not exposed to the renderer.
- Local API calls require a per-launch loopback token.
- Hosted API mode requires API-key identity resolving to `clientId`.
- Every route must use server-derived tenancy. Callers do not supply `clientId`.
- Audit logs are append-only JSONL and may contain client context. Export them deliberately.
- Diagnostics are metadata-only by default and exclude prompts, raw artifacts, model responses, and secrets.
- API keys are scoped to either `full` or `public` access, restricting public callers to designated public agent IDs and safe routes (`src/server/scope.ts`).
- Remote endpoints apply pre-auth IP rate limits and identity-based sliding-window rate limits to prevent abuse (`src/server/rateLimit.ts`).
- Outbound webhooks and external requests are validated against private IP ranges, loopbacks, metadata services, and unpermitted schemes (`src/server/webhooks/urlGuard.ts`, `src/util/safeFetch.ts`).
- Per-client and per-visitor daily spend ceilings are enforced synchronously before executing runs or gateway model calls (`src/runtime/intakeBudget.ts`, `src/runtime/gatewayBudget.ts`).
- Lead records contain personal contact information stored as JSON files on disk under the configured data root (`src/server/leads/store.ts`).
- The outbound address blocklist also covers IPv6 forms that embed or translate IPv4 (IPv4-compatible `::/96`, 6to4 `2002::/16`, Teredo `2001::/32`, local NAT64 `64:ff9b:1::/48`, site-local `fec0::/10`) (`src/util/netGuard.ts`).
- Untrusted web content is NFKC-normalized and stripped of zero-width and bidi characters before injection detection, and is wrapped in a random-id fence that page content cannot forge (`src/policy.ts`). Pattern detection is a tripwire; deterministic citation verification and the human gate are the boundary.
- Webhooks carry `X-Jantra-Timestamp`, a timestamp-bound `X-Jantra-Signature-V2`, and `X-Jantra-Delivery` for deduplication. Receivers should verify V2 (see `docs/THREAT_MODEL.md`); the legacy `X-Jantra-Signature` is replayable.
- The origin refuses public-scope keys unless the request carries the edge's shared secret (and refuses them entirely while `JANTRA_EDGE_SECRET` is unset), so a leaked public key cannot bypass the edge or spoof `X-Jantra-Client-IP` (`src/server/auth/apiKeys.ts`).
- With `TURNSTILE_SECRET_KEY` set on the Worker, creating a run or a lead requires a Cloudflare Turnstile token; verification fails closed and checks the token's hostname (`deploy/cloudflare-worker/worker.js`).
- Audit JSONL lines are hash-chained (`seq`, `prevHash`, `hash`; HMAC-SHA256 with `JANTRA_AUDIT_HMAC_KEY`). Check a run with `GET /v1/runs/:runId/audit/verify` (full scope; add `anchorSeq`/`anchorHash` from a webhook's `auditHead` to detect truncation) or `verifyAuditFile` in `src/audit.ts`. Appends take a per-file lock so separate processes cannot fork a chain.
- Public runs are bound to their creator: `POST /v1/runs` with a public key returns a one-time `runToken` (only its hash is stored), required as `X-Jantra-Run-Token` for every later public call on that run, including linking a lead (`src/server/runAccess.ts`).
- In remote mode `X-Forwarded-For` is trusted only when the connecting peer is an internal proxy address (`JANTRA_TRUSTED_PROXIES`, default private ranges and CGNAT). Fastify 5.12 ignores numeric hop counts, so the old `trustProxy: 1` would have put every visitor in one rate-limit bucket.
- CI runs `scripts/audit-gate.mjs` (dependency advisories) and `scripts/secret-scan.mjs` (tracked files) on every pull request.
- API responses carry `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`. The HTML report export also carries a strict CSP, embedded in the document too so `blob:` copies stay protected.
- Desktop: renderers are sandboxed, external links open in the system browser, report windows get no preload, the main window cannot navigate away from the app, and IPC only answers the main window's app URL (`desktop/src/electronSecurity.ts`).
- Connector credentials are AES-256-GCM encrypted and bound to `(clientId, connector)` as associated data (`v2:` format); legacy `v1:` blobs are re-encrypted at startup and on read.
- Runtime: Node 22 LTS everywhere (Docker image, CI, `engines`, `.nvmrc`). The production image is multi-stage; the C++ toolchain used to build better-sqlite3 exists only in the build stage.
- Threat model, residual risks, and open recommendations: `docs/THREAT_MODEL.md`.
